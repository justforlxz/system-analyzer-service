## 1. 时间模型与术语

一次诊断的对象是一次**启动实例**，由 `(machine_id, boot_id)` 唯一确定。一次启动实例可以有多次
采集（多个 `collection_id`），它们共享同一条时间轴。

| 术语 | 含义 | 现在的载体 |
| --- | --- | --- |
| boot 内部位置 | 从这次启动的单调时钟零点开始经过的纳秒数 | `monotonic_ns`（`clock_domain = boot_monotonic`） |
| 墙钟时刻 | Unix 纪元以来的纳秒数 | `realtime_ns` |
| 时钟域 | 一组可以直接相互比较的时间读数 | `(machine_id, boot_id, 时钟种类)`，见第 2 节 |
| 启动锚点 | 单调时钟零点在墙钟上的位置，即这次启动发生的墙钟时刻 | Boot 实体的 `started_realtime_ns`；没有记录时按第 4 节从记录推算 |
| 漂移 | 同一时钟域内，不同记录推算出的启动锚点之差 | 读取时算出，不写进记录，见第 4 节 |

三条总规则：

1. **boot 内的一切排序、对齐、回放都用 boot 内部位置，不用墙钟。** 墙钟只用于跨启动、跨机器
   比较和给人看的时间文字（第 10 节）。
2. **能直接比较的只有同一时钟域内的读数。** 跨时钟域只能通过第 4 节的换算，且必须带上误差。
3. **换算不写回记录。** 记录是不可变的事实（0.2 第 1 节），换算结果、误差、置信度都属于读取方
   的临时计算，不修改 `records.jsonl`。

## 2. `clock_domain` 的取值与时钟域划分

`clock_domain` 是闭集合，v1 只有两个取值。新增取值属于格式变更，需要升主版本（`docs/bootrec-v1.md`
第 7 节的兼容规则）。

| 取值 | 含义 | 出现场景 | 能否与另一个取值换算 |
| --- | --- | --- | --- |
| `boot_monotonic` | 这条记录的位置由单调时钟读数确定，`monotonic_ns` 非空 | SSH 采集的资源采样（3.4）、Systemd 生命周期（3.4）、Journal 导入里带 `__MONOTONIC_TIMESTAMP` 的条目（1.4） | 能换成墙钟，前提是知道启动锚点（第 4 节），误差为漂移 |
| `wall_realtime` | 这条记录只有墙钟读数，`monotonic_ns` 为空 | 只有墙钟的外部数据：第三方导出的日志、没有 `__MONOTONIC_TIMESTAMP` 的外来 Journal 条目、从别的系统按时间戳整理出来的事件 | 能换成 boot 内部位置，前提是知道启动锚点；不知道锚点时**不可换算**（第 4 节） |

**判定规则（唯一，不留选择余地）：**

```text
monotonic_ns 非空          → clock_domain = boot_monotonic
monotonic_ns 为 null       → clock_domain = wall_realtime
```

理由：0.2 把该字段定义为「`monotonic_ns` 所在的时间域」，而 `monotonic_ns` 非空时它只可能来自
单调时钟，为空时这条记录的位置只可能来自墙钟。两种情形穷尽了所有合法记录，所以这个字段没有
第三种值可用，也不需要第三种值。`monotonic_ns` 与 `realtime_ns` 同时为空在 0.2 就是非法记录
（`E_NO_TIMESTAMP`）。

由此得到一条生产者义务：**`clock_domain = wall_realtime` 的记录，`monotonic_ns` 必须是 `null`。**
v1 校验器不检查这一条（见第 11 节），读取方按本规则解释。

### 2.1 时钟域怎么划分

时钟域不是单个字段，而是一个元组：

```text
clock_domain_key(record) = (record.machine_id, record.boot_id, record.clock_domain)
```

两个读数可以直接比较，当且仅当它们属于同一个 `boot_monotonic` 时钟域。

| 比较对象 | 能否直接比较 | 依据 |
| --- | --- | --- |
| 同一 `(machine_id, boot_id)` 内的两条 `boot_monotonic` 读数 | 能 | 同一个单调时钟零点，同一台机器的同一个内核时钟 |
| 同一机器、不同 `boot_id` | 不能 | 零点不同，重新启动后单调时钟从头开始 |
| 不同 `machine_id` | 不能 | 零点与时钟源都不同 |
| 两条 `wall_realtime` 读数 | 能，但精度受限 | 都是 Unix 纪元时间；精度取决于各自的墙钟是否被同步过 |
| `boot_monotonic` 与 `wall_realtime` | 只能换算，不能直接比较 | 需要启动锚点（第 4 节） |

两台机器或两个 boot 之间无法直接比较时，**表达方式**是明确写出来，而不是勉强算一个数：

- 数据层面：各自保持自己的时钟域，记录上不改任何字段。
- 展示层面（4.2）：把两个 boot 画成两条独立的相对时间轴，横轴文字是「启动后 N 秒」，
  不出现跨 boot 的时间差。
- 需要跨启动看趋势时（例如「这次启动比上次慢了 3 秒」），比较的是**同一个观测口径下的相对位置**
  （例如「桌面会话建立」这个 Span 的 `end_monotonic_ns`），不是两个原始读数之差。

## 3. `monotonic_ns` 的零点与跨启动比较

### 3.1 零点定义

> `monotonic_ns` 的零点 = **这次启动的内核 `CLOCK_MONOTONIC` 零点**，即内核建立单调时钟的那一
> 瞬间。它不是采集开始的时刻，也不是采集脚本启动的时刻。

为什么选内核零点，而不是采集开始时刻：

1. **Journal 的时间戳本来就是这个零点。** journald 的 `__MONOTONIC_TIMESTAMP`、systemd 的
   `ActiveEnterTimestampMonotonic` 都以它为零点。选采集开始为零点，就要给每一条日志、每一个
   systemd 时间戳做一次平移，多一次计算就多一次出错的机会，而且平移量本身还要存。
2. **多次采集天然对齐。** 同一次启动的两次采集各自从不同时刻开始，但零点相同，所以两次采集的
   记录可以直接按 `monotonic_ns` 落在同一条轴上，不需要配准（第 7 节）。
3. **零点本身可以反推。** 任意一条同时带两个时钟的记录，用它自己的 `realtime_ns -
   monotonic_ns` 就能算出启动锚点（第 4 节），不需要额外的采集前导。

由此产生的采集义务（3.x 的采集插件）：取时间必须读**绝对读数**
`clock_gettime(CLOCK_MONOTONIC)` 得到的纳秒数，禁止写「自采集开始以来的秒数」。后者看似等价，
实际上把零点变成了采集开始时刻，会让同一 boot 的两次采集无法对齐，而且无法定位到 Journal 的
时间戳上。

### 3.2 跨启动比较的允许方式与禁止方式

| 方式 | 结论 | 说明 |
| --- | --- | --- |
| 把两个 boot 的记录放进同一个按 `monotonic_ns` 排序的序列 | **禁止** | 零点不同，排序结果没有任何物理含义，还会把不同启动的事件排到一起 |
| 把两个 boot 的 `monotonic_ns` 相减，当作「两次事件间隔」 | **禁止** | 减出来的是「A 次启动后 x 秒」与「B 次启动后 y 秒」的差，不是时间间隔 |
| 比较两个 boot 在同一个相对位置上的事件（都以「启动后 N 纳秒」表达） | 允许 | 这是跨启动比较的正确方式，例如比较两次启动的服务激活耗时 |
| 通过启动锚点把两个 boot 各自映射到墙钟，再比较 | 允许，必须带误差 | 误差至少是两侧锚点的漂移（第 4 节）；墙钟可能被 NTP 调整过，无法量化的部分要标注「误差未知」 |
| 用 `boot_index` 判断先后 | 允许 | Boot 实体的 `boot_index` 可以判先后，但它不提供时间差 |

一条具体禁令：**任何按 `monotonic_ns` 排序的结果，必须先按 `(machine_id, boot_id)` 分组。**
跨分组排序在 1.5 的查询里直接拒绝，不要返回一个看起来合理但无意义的顺序。

## 4. `boot_monotonic` 与 `wall_realtime` 的换算与漂移

### 4.1 公式

对同一 `(machine_id, boot_id)` 的任意一条记录：

```text
realtime_ns ≈ boot_start_realtime_ns + monotonic_ns + drift
monotonic_ns ≈ realtime_ns - boot_start_realtime_ns - drift
```

其中：

```text
boot_start_realtime_ns = realtime_ns - monotonic_ns        （由本条记录直接算出，drift 已含在里面）
```

同一条记录同时带两个读数时，这个换算是**定义式**，不需要额外信息；两个读数缺一个时才需要锚点。

### 4.2 换算方向与前提

| 方向 | 前提 | 结果 | 前提不满足时 |
| --- | --- | --- | --- |
| `boot_monotonic` → 墙钟 | 有启动锚点（Boot 实体的 `started_realtime_ns`，或同 boot 内其它记录算出的锚点） | `锚点 + monotonic_ns`，误差取漂移 | 标注「墙钟位置未知」，不猜 |
| `wall_realtime` → boot 内部位置 | 有启动锚点 | `realtime_ns - 锚点`，误差取漂移 | **不可换算**：这条记录保持在 `wall_realtime` 时钟域，不进 boot 内排序，只在界面上按墙钟文字显示 |
| 同 boot 内的两个读数相互比较 | 同属 `boot_monotonic` | 直接相减 | — |

锚点从哪来，按优先级：

1. Boot 实体的 `started_realtime_ns`（采集时直接记录，如 `uptime -s`）。
2. 同 boot 内任意一条同时带两个时钟的记录的 `realtime_ns - monotonic_ns`。
3. 都没有 → 没有锚点，`wall_realtime` 记录不可换算。

多个锚点候选时取**中位数**，极差就是漂移（4.4 节）。

### 4.3 漂移从哪来

| 来源 | 现象 | 本规范的处理 |
| --- | --- | --- |
| NTP 校时把墙钟往前或往后拨 | 同一 boot 内不同时刻算出的锚点不相等 | 不修正记录；比较时用锚点中位数，极差作为漂移写明 |
| RTC 初值不准 | 启动早期的墙钟时刻整体偏差一个固定量 | 同上：这个偏差是系统性的，不影响 boot 内排序 |
| Journal 只有微秒精度 | 换算成纳秒后低三位恒为 0 | 量化误差按 ±500 ns 计，不用别的字段补低位 |
| 系统休眠 | 单调时钟在休眠期间不前进，墙钟继续前进 | 本次未在验证机上验证休眠行为（见第 13 节）；发现锚点极差异常增大时按漂移处理，不引入专门机制 |

本规范只依赖单调时钟的两个性质：**同一个 boot 内单调递增、不受 NTP 影响**。不依赖它具体取自
`CLOCK_MONOTONIC` 还是 `CLOCK_BOOTTIME`——两者的差别只在系统休眠时出现，属于上表最后一行。

### 4.4 误差怎么记录（单位：纳秒）

0.2 的记录里没有放误差的字段，也不允许为了误差加字段。误差因此按下面的方式表达，全部是读取时
算出的值：

| 量 | 怎么算 | 单位 | 写在哪 |
| --- | --- | --- | --- |
| 量化误差 | 来源只有微秒精度时取 500 | 纳秒 | 读取方的查询结果（1.5 定字段名） |
| 单条记录的锚点 | `realtime_ns - monotonic_ns` | 纳秒 | 不落库，只在内存里用于换算 |
| 漂移（boot 级） | 同一 boot 内各锚点候选的**极差** `max - min` | 纳秒 | 同上；时间线界面据此决定是否给这个 boot 打「墙钟不可靠」标记 |
| 跨启动/跨机器换算误差 | 两侧漂移之和，另加无法量化的墙钟调整 | 纳秒 | 同上；无法量化时必须写「误差未知」，不得写成 0 |

建议阈值（下游可以覆盖）：boot 级漂移极差 > 1 秒时，这个 boot 的墙钟换算不用于跨启动比较，
只用于显示时间文字。理由：1 秒以内的偏差不影响人读时间，超过 1 秒说明发生过校时，跨启动
比较的结论会被污染。

**真实测量**（验证机 10.20.50.152，2026-11-11，最近 200 条日志，覆盖 2 小时 5 分 22 秒）：

```text
锚点候选 200 个：min 1794191589381562、max 1794191589381564、中位数 1794191589381563
极差 = 2 µs = 2000 ns
```

200 个锚点候选只差 2 微秒，说明这段窗口内墙钟没有被拨动，剩下的 2 微秒就是两个微秒读数各自的
舍入（1 微秒）。同一时刻用 `uptime -s` 得到的启动时刻是 `2026-11-09 10:33:09 CST`，与中位数
`1794191589381563 ns`（= `2026-11-09T02:33:09.381563Z`）落在同一秒，两种独立来源互相印证。

## 5. Journal 时间戳的换算细则

### 5.1 字段映射

| Journal 原始字段 | 单位 | 落到模型 | 换算 |
| --- | --- | --- | --- |
| `__MONOTONIC_TIMESTAMP` | 微秒（µs） | `monotonic_ns` | `× 1000`；缺失 → `null`，且 `clock_domain = wall_realtime` |
| `__REALTIME_TIMESTAMP` | 微秒（µs） | `realtime_ns` | `× 1000`；缺失 → 该条目不能进 `journal.jsonl`（0.2 要求必填） |
| `_SOURCE_REALTIME_TIMESTAMP` | 微秒（µs） | `fields` 里的原值 | 只保留原文，**不参与**定位 |
| `_BOOT_ID` | 32 位小写十六进制 | `boot_id` | 插入连字符，变成 8-4-4-4-12，见 5.2 |
| 其余 `_*`、`SYSLOG_*`、`PRIORITY` 等字段 | — | `fields` | 原样保留为字符串 |

单位处理只有乘 1000 这一步。0.2 把两个时间字段定成 `int64` 纳秒，换算结果必须在它之内
（`2**63 - 1` 纳秒约等于 292 年）：超出就报错，不静默溢出成负数或截断。

由此得出两条不能做的事：

- **不要把换算后的纳秒当成真的有纳秒精度。** 低三位恒为 0，任何计算都要按 ±500 ns 看待。
- **不要用别的字段补低位。** `_SOURCE_REALTIME_TIMESTAMP` 与 `__REALTIME_TIMESTAMP` 是两个不同
  的读数（前者是产生日志的程序写的时间，后者是 journald 收到的时间），拼在一起不是精度提升，
  是造假。

`__CURSOR` 里的 `m=` 与 `t=` 是同样两个值的十六进制写法（微秒），可以拿来自检：

```text
m=28f0558613 → 0x28f0558613 = 175830828563 µs = monotonic_ns 175830828563000
t=65ff7b8ad9bcf → 0x65ff7b8ad9bcf = 1794367420210127 µs = realtime_ns 1794367420210127000
```

### 5.2 Boot ID 的归一化

同一个值有两种写法，比较前必须统一：

| 来源 | 写法 | 例子 |
| --- | --- | --- |
| `/proc/sys/kernel/random/boot_id`、模型里的 `boot_id` | 小写、带连字符、36 字符 | `abc7451f-65c8-4be8-ab01-4b9a1e49a8b9` |
| journald 的 `_BOOT_ID`、`journalctl --list-boots` | 小写、无连字符、32 字符 | `abc7451f65c84be8ab014b9a1e49a8b9` |

归一化规则：去掉连字符、转小写、要求恰好 32 位十六进制，再按 8-4-4-4-12 插回连字符。
模型里的 `boot_id` 采用 `/proc` 的形式（0.2 第 5.2 节），所以 `_BOOT_ID` 必须转换后才能与
manifest、与 Boot 实体比较。`.bootrec` 里的四份样例用的也是带连字符的形式。

跳过这一步的后果很具体：同一个 boot 会被当成两次启动，`journal.jsonl` 的
`E_JOURNAL_SCOPE` 检查会全部失败，或者更糟——导入方自己放宽比较，把不同启动的日志混进一份文件。

`_MACHINE_ID` 不做归一化：它是 systemd 的机器标识（`/etc/machine-id`），而模型里的 `machine_id`
由部署方生成（例如 `machine:<hostname>`），两者不自动等价。关联一律以 `machine_id` 为准，
`_MACHINE_ID` 只能进 `fields` 当证据。

### 5.3 真实事件示例

取值方式（只读，不修改验证机）。本例是一条具体的日志，用它的 `__CURSOR` 精确取出来：

```bash

  's=ee9702b862c943f8b9fcf0bfaa016180;i=c87c6;b=abc7451f65c84be8ab014b9a1e49a8b9;m=28f0558613;t=65ff7b8ad9bcf;x=65e3ca9f69fc6ea2'" \
  > ./entry.export
```

```text
_SYSTEMD_INVOCATION_ID=39b369d1e917432bb0a9bb9d4df7d03e
MESSAGE=     uos : PWD=/home/uos ; USER=root ; COMMAND=/usr/bin/id -u root
_SOURCE_REALTIME_TIMESTAMP=1794367420210120
```

`-o export` 里除了 `字段=值` 这种行，还有二进制字段：字段名单独一行，随后是 8 字节原生长度
（64 位 Linux 上是小端），再跟同样字节数的原始内容，其中可以有换行和非 UTF-8 字节。`SYSLOG_RAW`
就是这种，验证机这次启动的 Journal 里有 566 处。换算法只认上面列出的那几个字段，二进制字段
一律跳过，所以把它们留在输入里不影响换算：

```bash
# 整份导出同样可以直接喂进去（工具只取第一条事件），二进制字段不影响解析
ssh uos@10.20.50.152 'journalctl -o export -b --no-pager -n 200' > ./journal.export
cd backend && uv run python -m system_analyzer.tools.journal_time ../journal.export
```

换算过程共四步：

| 步骤 | 计算 | 结果 |
| --- | --- | --- |
| 1. Boot ID 归一化 | `abc7451f65c84be8ab014b9a1e49a8b9` → 8-4-4-4-12 | `abc7451f-65c8-4be8-ab01-4b9a1e49a8b9` |
| 2. 单调时钟 | `175830828563 µs × 1000` | `monotonic_ns = 175830828563000`（启动后 2 天 0 小时 50 分 30.828563 秒） |
| 3. 墙钟 | `1794367420210127 µs × 1000` | `realtime_ns = 1794367420210127000`（UTC 2026-11-11T03:23:40.210127Z，即 CST 11:23:40） |
| 4. 启动锚点 | `1794367420210127000 − 175830828563000` | `1794191589381564000`（UTC 2026-11-09T02:33:09.381564Z，即 CST 10:33:09） |

这条事件在 boot 时间轴上的位置就是第 2 步的 `175830828563000` 纳秒。`clock_domain =
boot_monotonic`，因为它有单调读数。

**换算结果（`python -m system_analyzer.tools.journal_time` 的实际输出）**

```text
boot_id: abc7451f-65c8-4be8-ab01-4b9a1e49a8b9
clock_domain: boot_monotonic
monotonic_ns: 175830828563000
boot_relative: 2d 00:50:30.828563000
realtime_ns: 1794367420210127000
realtime_utc: 2026-11-11T03:23:40.210127+00:00
source_realtime_ns: 1794367420210120000
boot_start_realtime_ns: 1794191589381564000
```

复算方式（三条独立来源互相对得上，读者可以逐条重跑）：

```bash
# 1. 工具本身：把上面那条事件喂进去（上面那条 cursor 命令落下的 entry.export，
#    或者把原始字段块另存成文件；整份 journalctl 导出也可以，工具只取第一条事件）
cd backend && uv run python -m system_analyzer.tools.journal_time ../entry.export

# 2. journalctl 自己按 boot 内秒数打印同一条日志，得到 [175830.828563]
ssh uos@10.20.50.152 'journalctl -o short-monotonic -b --no-pager | grep "COMMAND=/usr/bin/id -u root"'

# 3. 启动锚点与 uptime -s 对照，得到 2026-11-09 10:33:09（CST）
ssh uos@10.20.50.152 'uptime -s'
```

三条来源的关系：第 2 条印证第 2 步（`[175830.828563]` 与 `2d 00:50:30.828563000` 是同一个数
的两种写法），第 3 条印证第 4 步（启动锚点落在 `uptime -s` 的同一秒）。`_SOURCE_REALTIME_TIMESTAMP`
比 `__REALTIME_TIMESTAMP` 早 7 微秒，这是「程序写入」与「journald 收到」的差，不参与定位。

另外核实过的事实：这次启动的 16513 条日志全部同时带 `__MONOTONIC_TIMESTAMP` 与
`__REALTIME_TIMESTAMP`。所以「Journal 条目缺单调读数」这次**没有在验证机上观察到**，第 5.1 节
对缺失的规定来自 0.2 的字段表（部分内核与外来来源的日志没有），不是实测结论。

## 6. `Span` 开放区间的收尾规则

`end_monotonic_ns` 或 `end_realtime_ns` 为 `null` 的语义在 0.2 已经固定：**采集结束时该过程仍未
结束**。时间线怎么画，由本节定：

| 规则 | 内容 |
| --- | --- |
| 收尾时刻 | 用**所属 collection 的采集窗口终点**：该 collection 内所有记录时间字段（含 `end_*_ns`）的最大值 |
| 视觉 | 区间画到收尾时刻，末端标注「未闭合」（虚线或开口端），与已闭合区间明显不同 |
| 记录 | 不修改记录，不把收尾时刻写进 `end_*_ns`；`null` 永远是 `null` |
| 多次采集 | 开放区间只在其所属 collection 的窗口内有效。下一份采集里没有再次观测到该实体时，两段之间画「未知」缺口，不得跨空档接续 |
| 再次观测到 | 下一份采集里又出现了该实体的活跃证据，就按新记录新开一段，不去延长上一段（记录不可变） |
| 只有墙钟的记录 | `end_realtime_ns` 非空而 `end_monotonic_ns` 为 `null` 时，按墙钟收尾，不换算成单调时间 |

禁止的收尾方式，以及为什么：

- **禁止用「查询时刻」「当前时间」收尾。** 同一份数据在不同时间回放会得到不同长度的区间，
  违反「可重复回放」。
- **禁止用导入时间、文件写入时间收尾。** 那是数据的搬运时刻，不是系统事实。
- **禁止把 `null` 收尾成「启动结束时刻」或「最后一条日志时刻」而不标注。** 未闭合是一个事实，
  抹掉它会让「服务一直在跑」与「服务在采集结束前停了但没记录到」变得无法区分。

## 7. 多次采集的对齐与去重

### 7.1 对齐

同一 `(machine_id, boot_id)` 下的所有 collection 共享同一个单调时钟零点（第 3.1 节），因此：

- **不做平移、不做缩放。** 直接把各 collection 的记录按 `monotonic_ns` 放到同一条轴上。
- **墙钟换算按 collection 各算各的。** 上一次采集与下一次采集之间可能发生校时，用一个全局锚点
  会把误差摊到所有记录上。展示墙钟文字时，用该记录所属 collection 的锚点。
- **排序键**：`(monotonic_ns, collection_id, record_id)`。带上后两个是为了同一纳秒有多条记录时
  顺序稳定，不同次查询得到同一个顺序。

### 7.2 去重

去重分两级，与 0.2 第 8 节一致，这里只说时间线上的表现：

| 情形 | 判定 | 处理 | 禁止 |
| --- | --- | --- | --- |
| 同一个 `collection_id` + 同一个 `record_id` | 同一次采集的同一事实 | 导入时跳过，时间线上只出现一次 | 当成两条不同记录 |
| 不同 `collection_id`，内容完全相同 | 两次采集各自观测到同一状态，是两条独立事实（`record_id` 的摘要里含 `collection_id`，所以两者的 `record_id` 仍然不同） | 两条都保留 | 按内容合并、删掉一条 |
| 两次采集的时间范围重叠，同一实体同一时刻有两条记录 | 重叠观测 | 时间线在重叠区间只画最靠近游标的一条，并把重叠区间标注出来 | 把重叠当成数据重复而删除记录，或把两条都画（会看起来像抖动的双线） |
| 两次采集之间存在空档 | 空档期间没有观测 | 画「无数据」缺口，曲线断开 | 用直线连接空档两侧，或用 0 填充 |

为什么重叠时不能删记录：`.bootrec` 记录是不可变的事实（0.2 第 1 节），删掉一条就丢失了「这个
时刻被观测过两次」这个信息，也无法判断两条是否真的一致。去重只发生在**导入的幂等键**上，
不发生在时间线的绘制上。

## 8. 采样数据：起止、间隔、抖动与缺失

一条 Metric 记录就是一个采样点，序列由 `(source_plugin, stream_id, entity)` 确定（0.2 第 4.3
节）。模型里**没有**「期望采样时刻」「采样周期」「抖动」字段，也不为此加字段，全部按下面推导：

| 量 | 怎么得到 |
| --- | --- |
| 采样起点 | 这条流第一条记录的 `monotonic_ns` |
| 采样终点 | 这条流最后一条记录的 `monotonic_ns` |
| 采样间隔 | 相邻两条记录的 `monotonic_ns` 之差 |
| 标称周期 | 采集插件的配置值，不写进记录；界面上显示的周期文字取这个值 |
| 采集抖动 | 实际间隔 − 标称周期；不带符号地展示时用绝对值 |
| 缺口 | 实际间隔明显大于标称周期（建议阈值：大于 2 倍标称周期）即视为缺口，曲线断开并标注「无数据」 |

抖动和缺口是**读取时算出来的**，所以同一份数据任何时候回放都得到一致的结论。采集插件不需要
记录自己「抖了一下」，也不需要补一条「这里缺了」的记录。

### 8.1 采样数据缺失时的表现

与 `data-model.md` 第 7 节一致，落到时间线上：

| 缺失情况 | 数据层 | 时间线表现 |
| --- | --- | --- |
| 单个采样点没采到 | 不写这条 Metric 记录（不写 0、不写 `null`、不写 `NaN`） | 曲线在缺口处断开，不插值、不连线 |
| 一条指标流整段没数据 | `metric_stream` 实体 `available = false` + `unavailable_reason`，这条流没有任何 Metric 记录 | 该轨道整体显示「不可用：<原因>」，不画 0 值曲线 |
| 一条流部分区间没数据 | 与单点缺失相同 | 缺口处断开并标注，轨道本身仍然存在 |
| 整份文件没有资源指标（Journal-only 导入） | `manifest.resources.available = false`，`resources.reason` 写明原因 | 只显示 Journal 与服务生命周期轨道，资源轨道整体不出现，并说明「本次导入不含资源数据」 |

三条不能做的事：**不能把缺失画成 0**（0% 的 CPU 是一个有效测量值）、**不能跨缺口连线**、
**不能补一条「无数据」事件来代替 Metric 记录**。

## 9. 实体关联规则表

关联只用 0.2 第 6 节列出的键，本节补充每个键的**前提**与**失效条件**——也就是什么时候这个键
不再能证明「是同一样东西」。

| 关联键 | 来源字段 | 关联到 | 关联前提 | 失效条件 |
| --- | --- | --- | --- | --- |
| Machine ID | `machine_id`（`_MACHINE_ID` 只作证据） | Machine 实体 | 同一个值在同一台机器上长期稳定 | 重装系统、改主机名导致 `machine_id` 变化；虚拟机从快照恢复会把 `machine_id` 一起带回，于是两台机器同 id。因此跨机器连接必须同时核对 `hostname` 与采集来源 |
| Boot ID | `_BOOT_ID`、`/proc/sys/kernel/random/boot_id`、`bootrec` 的 `collection.boot_id` | Boot 实体 | 归一化成同一写法后完全相等（5.2 节） | 每次重启内核重新生成，所以跨启动不能用它关联同一个服务；从虚拟机快照恢复会带回同一个 `boot_id`，于是同一 id 出现在不同机器上。因此连接键必须是 `(machine_id, boot_id)` 二元组 |
| PID | `_PID`、`SYSLOG_PID` | Process 实体（`attributes.pid`） | 同一个 boot 内、同一时间段内 PID 只对应一个进程 | 进程退出后 PID 会被复用；容器（`user@1000.service` 下的 podman 之类）里外的 PID 不是同一个进程。因此按 PID 关联必须带时间区间，不能只按 PID 值 EQUAL 连接 |
| Unit | `_SYSTEMD_UNIT`、`_SYSTEMD_USER_UNIT` | Service 实体 | 单元名在一次启动内指向同一个单元定义 | 单元 stop 后再 start 是两个运行实例（见下一行）；模板单元 `foo@bar.service` 必须按全名匹配，按 `foo@.service` 聚合会把所有实例混成一个 |
| Invocation ID | `_SYSTEMD_INVOCATION_ID` | 一次单元运行实例（Service 实体的生命周期区间） | systemd 每次激活单元生成新的 128 位 id，同一次运行内不变 | 非 systemd 管理的作用域（scope、直接运行的进程）没有这个字段；运行结束即失效。**重建服务生命周期必须用 Invocation ID，不能用 Unit 名**，否则一次重启会把两段运行画成一段 |
| cgroup | `_SYSTEMD_CGROUP` | cgroup 实体 | 同一 boot 内 cgroup 路径唯一指向一个控制组 | 控制组被销毁后路径可以被复用（尤其 `session-N.scope` 这种按会话编号命名的路径）；进程迁移到别的 cgroup 后，旧日志仍然指向旧路径。因此按 cgroup 关联也必须带时间区间 |

三条使用规则（与 0.2 第 6 节相同，这里再落到时间线上）：

1. 只用上表的键连接，不新增隐式约定（不按文件名、不按「同一行即同一实体」）。
2. 连接失败按「缺失」处理并报告，不猜测、不填充。
3. 跨启动的对比走第 3.2 节的对齐方式，不通过合并实体实现。

## 10. 排序：为什么禁止只按 realtime 排序

> **禁止只按 `realtime_ns` 排序启动过程的事件。**

四条原因，每条都能在这台验证机的数据上验证：

1. **墙钟会被拨动，单调时钟不会。** NTP 校时在启动过程中把墙钟往前或往后拨，按墙钟排出来的
   顺序在拨动点前后会倒错，甚至出现「后发生的事件时间更早」。同一次启动里，两次采集之间的拨动
   会直接破坏跨采集的排序。
2. **启动早期的墙钟不可信。** 内核启动到 NTP 同步之间，墙钟来自 RTC，偏差可达秒级；而这恰好是
   启动过程分析最关心的时段。
3. **不同启动会混在一起。** 两个 boot 的 `realtime_ns` 相近（甚至相同，例如同一次维护窗口里
   连续重启两次），只按墙钟排序会把不同启动的事件排到一起，而 `monotonic_ns` 各自从零开始。
   这就是「Boot ID 必须区分启动实例」在排序上的直接体现。
4. **单调读数在同一 boot 内保序。** 它是内核时钟，单调递增、不受校时影响，而且是 journald 与
   systemd 的原生时间基准，不需要二次换算。

正确做法：先按 `(machine_id, boot_id)` 分组，组内按 `monotonic_ns` 排序（第 3.2、7.1 节）。
墙钟只在两种情况下参与排序：

- 这条记录只有墙钟（`clock_domain = wall_realtime`），且没有锚点把它换算到 boot 内部位置。
  此时按 `realtime_ns` 排序，并在界面上标注「该事件位置未知 / 只有墙钟时间」。
- 跨启动比较（第 3.2 节），此时比较的是相对位置或已换算到墙钟的时刻，且必须带误差。

| 排序场景 | 排序键 | 说明 |
| --- | --- | --- |
| 一次启动内的事件、Span、Metric、Annotation | `monotonic_ns`（同值再按 `collection_id`、`record_id`） | 唯一正确的启动过程排序 |
| 只有墙钟的记录 | `realtime_ns` | 单独排，标注位置未知 |
| 跨启动的两次启动过程对照 | 各自分组内按 `monotonic_ns`，两条轴并排 | 不做跨组排序 |
| 机器列表、采集任务列表 | `realtime_ns` 或数据库时间 | 与启动过程无关，不受本禁令约束 |

## 11. 与 0.2 校验器的差距

`backend/src/system_analyzer/domain/bootrec.py` 的 `validate_bootrec` 只检查 0.2 定义的字段与
引用，**不检查**本文档新增的这两条语义：

| 本文档的要求 | 校验器现状 | 谁负责 |
| --- | --- | --- |
| `clock_domain = wall_realtime` 时 `monotonic_ns` 必须为 `null` | 不检查（只有 `E_NO_TIMESTAMP`：两者都为空） | 生产者按规范写；读取方按第 2 节解释 |
| `_BOOT_ID` 必须归一化成 `/proc` 形式后才比较 | 只做字符串相等，不做归一化（`E_JOURNAL_SCOPE` 因此可能误报） | 导入方（1.4）在写入 `journal.jsonl` 前归一化 |

为什么不在这一版补上校验：补充检查属于收紧校验规则，会改变 0.2 已定稿的「必填性/缺失语义」并
新增错误码，按 `docs/bootrec-v1.md` 第 7 节的兼容规则需要升版本。本任务的范围是定规范，
校验器与规范的差距在这里记下来，交给需要它的任务（1.4 归一化是导入方自己的义务，不是校验器的）。

## 13. 偏差清单

与 Task Handoff 相比，本任务的实际偏差：

1. **换算工具放在两个目录。** 纯换算规则在 `backend/src/system_analyzer/domain/time_base.py`，
   命令行在 `backend/src/system_analyzer/tools/journal_time.py`。理由：基线文档第 3 节把
   「时间基准与关联规则」划给 `domain/`，而 `tools/` 是命令行工具目录（现有
   `validate_bootrec`、`export_openapi` 都在那里）。1.5 要 import 的是 `domain.time_base`，
   它不应该依赖命令行模块。
2. **命令行工具认两种导出格式。** `-o json` 直接读第一行；`-o export` 按它实际写出的两种字段
   写法扫描：`字段=值` 行，以及「字段名一行 + 8 字节原生长度 + 原始字节」的二进制字段（如
   `SYSLOG_RAW`），后者整个跳过、不解码。长度头是原生 `size_t`，64 位 Linux 上是 8 字节小端；
   32 位系统上导出再拿到 64 位机器上读会失败，这种情况报「输入被截断，或不是 journalctl
   -o export 的格式」，不静默跳过。工具只取第一条事件，需要定位某一条具体日志时用 `--cursor`
   或 journalctl 的过滤条件。
3. **没有补校验器。** 见第 11 节。
4. **休眠行为未实测。** 第 4.3 节最后一行只说「发现锚点极差异常增大时按漂移处理」，没有做休眠
   实验；验证机是台式机，没有在此任务里制造休眠。
